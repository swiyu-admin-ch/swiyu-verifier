# Migration Guide: v4.0.x → v5.0.0

This guide helps you migrate from **v4.0.x** to **v5.0.0** of the Swiyu Verifier Service.

It is based on the **[5.0.0]** section in `CHANGELOG.md` and includes breaking changes related to
Trust Anchor configuration, audit data handling, verification trust model, and signing key management.

## Compatibility summary

- **Wallets / OID4VP clients:**
    - No direct breaking changes; however, trust resolution behavior has changed (see Trust Anchor section below).
    - Support for DCQL `trusted_authorities` is now available for improved credential filtering.
- **Business Verifiers:**
    - Trust Anchor declaration has moved from request-time to application-level configuration.
    - Audit information (`vp_token`, `credential_subject_data`, `credential_evaluation`) is now **omitted by default**
      and must be explicitly enabled.
    - Verifications can now be created without a source of trust, which may require updated business logic in the
      Business Verifier. Verifications will always be regarded as failed from the Generic Verifier point of view. As the
      data is now returned the logic can be customized in the business verifier.
- **Operators / DevOps:**
    - Environment variable `SWIYU_TRUST_ISSUER_DID` now declares a single Trust Anchor at startup (no longer via API).
    - Multiple signing keys can now be configured via `application.signing-keys` (non-breaking if not configured).
    - Trust Anchor validation has been hardened: a `Trust Anchor` without a configured `Trust Registry` will now fail.

## Breaking changes

Work through every applicable item in this section.

### 1. Trust Upgrades

**Before (v4.0.x):**
* The verifier supported both Trust Protocol 1.0 and Trust Protocol 2.0.
* Business verifiers could provide a `Trust Anchor` DID in the `CreateVerificationRequest`
at request time, allowing dynamic trust setup per verification.

**After (v5.0.0):**
* **Trust Protocol 1.0 has been completely removed**. Only Trust Protocol 2.0 is supported.
* The `Trust Anchor` has been **moved to application-level configuration** via the
environment variable `SWIYU_TRUST_ISSUER_DID` and is now **limited to a single trust anchor** (as per Trust Protocol
2.0).
The `CreateVerificationRequest` no longer accepts a `Trust Anchor` parameter.

**Note**: This impacts only verifiers that do not rely on `accepted_issuer_dids`

**Impact:**

- **Deployments using Trust Protocol 1.0 will not work** with v5.0.0.
- All trust functionality now depends on Trust Protocol 2.0 infrastructure.
- **Trust anchor is now immutable per deployment** — all verifications in an instance share the same trust anchor.
- Trust setup is no longer per-request, reducing flexibility but improving security and consistency.
- Multiple trust anchors are no longer supported in a single deployment.

**Action required:**

1. **Identify your current Trust Anchor:** The trust anchor is unique per environment. Check with the
   published [swiss profile trust](https://swiyu-admin-ch.github.io/specifications/swiss-profile-trust/) document the
   applicable DID & URLs.

2. **Move to environment configuration:** Set the `SWIYU_TRUST_ISSUER_DID` and `SWIYU_TRUST_REGISTRY_API_URL`
   environment variable in your
   deployment manifests:

   ```yaml
   # docker-compose.yml, Kubernetes Deployment, or Helm values
   environment:
     SWIYU_TRUST_REGISTRY_API_URL: "https://trust-reg.trust-infra.swiyu-int.admin.ch"
     SWIYU_TRUST_ISSUER_DID: "did:webvh:QmdVPcfEJgvQAJKEjaTWAhskT1kc59KZQiXNenqHBB7iH5:identifier-reg.trust-infra.swiyu-int.admin.ch:api:v1:did:4c131dc4-ced1-454b-bbd4-9401c7512e37"  # Your single trust anchor DID
   
   ```

3. **Update business verifier code:** Remove any code that attempts to set `Trust Anchor` in the verification request:

   ```java
   // Before (v4.0.x)
   CreateVerificationRequest request = new CreateVerificationRequest()
       .trustAnchor("did:tdw:...")
       .otherField("value");
   
   // After (v5.0.0)
   CreateVerificationRequest request = new CreateVerificationRequest()
       .otherField("value");
       // Trust anchor is now configured at the application level
   ```

4. **Handle multiple trust anchors (if applicable):** If your deployment requires multiple trust anchors:
    - This is **no longer supported** in a single verifier instance to prevent attacks causing Sandbox credentials being
      accepted in production.
    - Consider running **separate verifier instances**, each with its own `SWIYU_TRUST_ISSUER_DID` and
      `SWIYU_TRUST_REGISTRY_API_URL`
    - Alternatively, use a load balancer to route requests to different instances based on trust requirements.

**Testing:**
* After upgrading verify that trust registry queries succeed using Trust Protocol 2.0 endpoints.
* After upgrading verify that verification requests still succeed and that the verifier correctly
validates credentials against the trust anchor specified in `SWIYU_TRUST_ISSUER_DID`.

### 2. Audit information now omitted by default: explicit opt-in required

**Before (v4.0.x):** The management API response included audit information by default:

- `vp_token` — the VP token returned by the wallet
- `credential_subject_data` — the credential subject data
- `credential_evaluation` — credential evaluation results

**After (v5.0.0):** These audit fields are **omitted from responses by default** and must be explicitly enabled
via a new configuration property.

**Impact:**

- **API responses are leaner by default** — responses may be significantly smaller if audit data is large.
- **Privacy improvement** — sensitive audit data is not exposed unless explicitly requested.
- **Backward compatibility:** Clients expecting audit data in responses will need to enable it explicitly.

**Action required:**

1. **Identify clients that need audit data:** Review your business verifier and any downstream systems that
   consume verification management responses. The default values make it so no change occurs.

2. **Enable (audit) data (if needed):** If you need the presented data, verification details or the audit fields in
   responses, configure the new properties according to business case needs.
    * ADDITIONAL_AUDIT_INFORMATION_CREDENTIAL_SUBJECT_DATA_ENABLED -- Default True. This returns the requested data
    * ADDITIONAL_AUDIT_INFORMATION_VP_TOKEN_ENABLED -- Default false. This returns the whole presented VP token.
    * ADDITIONAL_AUDIT_INFORMATION_CREDENTIAL_EVALUATION_ENABLED -- Default false. This returns details of the
      credential evaluation. This can be used for audit purposes or having custom logic allowing certain states to be
      also acceptable. For example when a verification failed due to the state being suspended a business verifier may
      choose to still regard the verification as successful.

   ```yaml
   # Enable audit information in management API responses
   environment:
     ADDITIONAL_AUDIT_INFORMATION_CREDENTIAL_SUBJECT_DATA_ENABLED: "true",
     ADDITIONAL_AUDIT_INFORMATION_CREDENTIAL_EVALUATION_ENABLED: "false",
     ADDITIONAL_AUDIT_INFORMATION_VP_TOKEN_ENABLED: "false"
   ```

3. **Update client code:** If you have parsers or validators for the audit fields, ensure they handle the case
   where these fields are absent (either by making them optional or by enabling the configuration above).

   ```java
   // Before (v4.0.x) — audit fields always present
   VerificationResponseDto response = verificationService.getResult(verificationId);
   String vpToken = response.getVpToken();  // Always non-null
   
   // After (v5.0.0) — audit fields may be null unless enabled
   VerificationResponseDto response = verificationService.getResult(verificationId);
   String vpToken = response.getVpToken();  // May be null if audit data not enabled
   if (vpToken != null) {
       // Process audit data
   }
   ```

### 4. Verification without source of trust: allow creation without `accepted_issuer_dids` or Trust Anchor

**Before (v4.0.x):** Verification requests required **either** `accepted_issuer_dids` **or** a `Trust Anchor`
to be configured, ensuring a source of trust was always established upfront.

**After (v5.0.0):** Verification can now be created **without a source of trust**, allowing trust verification
to be performed **later** in the workflow. This is useful for scenarios where trust is established 
by a downstream system.

**Impact:**

- **Reduced coupling:** Verifications can be initiated before trust configuration is fully determined.
- **Flexibility:** Business logic can defer trust decisions until credential evaluation time.
- **Risk:** Without careful application design, this could allow unverified credentials to be accepted.

**Action required:**

1. **Review trust logic:** Audit your application to ensure that if you create a verification without a source
   of trust, trust verification is **always performed later** before accepting the credential.

2. **No configuration change needed:** This change is backward compatible. Existing code that provides a source
   of trust will continue to work as before.

3. **Optional: implement deferred trust verification:** If your business logic requires deferred trust, update
   your code to validate trust at a later stage:

   ```java
   // Example: Create verification without source of trust
   CreateVerificationRequest request = new CreateVerificationRequest()
       // Note: no accepted_issuer_dids or Trust Anchor
       .otherField("value");
   
   // Later, when credential is received, verify trust
   VerificationResponseDto response = verificationService.getResult(verificationId);
   if (response.isCredentialSubmitted()) {
       // Perform trust verification here
       validateTrust(response.getCredentials());
   }
   ```

**Testing:** Create a verification request without `accepted_issuer_dids` or Trust Anchor and confirm it
succeeds (should not fail due to missing trust configuration).

### 5. Deprecated cache properties removed: `caching.jwk-cache-ttl` and `caching.trust-cache-ttl`

**Before (v4.2.x):** Cache TTL properties used millisecond units but had confusing names:

- `caching.jwk-cache-ttl` (renamed to `caching.jwk-cache-ttl-ms` in v4.2.0)
- `caching.trust-cache-ttl` (renamed to `caching.trust-cache-ttl-ms` in v4.2.0)

**After (v5.0.0):** The **old property names have been completely removed**. Only the explicit `-ms` suffixed
versions are supported.

**Impact:**

- **Startup failure if old properties are used** — the verifier will fail to start with a configuration error.
- This ensures clarity around time units (milliseconds).

**Action required:**

1. **Search your configuration files** for the old property names:
    - `caching.jwk-cache-ttl`
    - `caching.trust-cache-ttl`

2. **Rename to the new versions:**

   ```yaml
   # Before (v4.1.x or earlier)
   caching:
     jwk-cache-ttl: 3600000
     trust-cache-ttl: 1800000
   
   # After (v5.0.0) — REQUIRED
   caching:
     jwk-cache-ttl-ms: 3600000
     trust-cache-ttl-ms: 1800000
   ```

3. **Check environment variables:** If you use environment variables, rename them:

   ```bash
   # Before (no longer works)
   export CACHING_JWK_CACHE_TTL=3600000
   export CACHING_TRUST_CACHE_TTL=1800000
   
   # After (v5.0.0) — REQUIRED
   export CACHING_JWK_CACHE_TTL_MS=3600000
   export CACHING_TRUST_CACHE_TTL_MS=1800000
   ```

**Testing:** Start the verifier and confirm it initializes without configuration errors.

## Non-breaking enhancements

The following changes improve functionality but do **not** require action:

### Multiple signing keys support (non-breaking if not configured)

The verifier now supports **multiple signing keys** via the `application.signing-keys` configuration,
preparing for the **did:tdw → did:webvh migration**. If this configuration is not changed, the verifier
uses the existing single signing key by default.

**Optional action (recommended for migration planning):**

If you are preparing for a key rotation or migration, you can now configure multiple keys:

```yaml
# New configuration (optional)
application:
    signing-keys:
        -   keyId: "key-1"
            key: "..."
        -   keyId: "key-2"
            key: "..."
```

The verifier will use the first key for signing by default, but all configured keys can be used for
verification (enabling a gradual migration).

### Support for DCQL Trusted Authorities

The verifier now supports **DCQL `trusted_authorities`** provided by wallets. When using
`accepted_issuer_dids` to establish trust, ensure that the DCQL `trusted_authorities` match the DIDs
provided.

If `trusted_authorities` are not set in the DCQL query and `accepted_issuer_dids` is configured,
the `trusted_authorities` will be **automatically populated from `accepted_issuer_dids`**, allowing
wallets to filter possible credentials.

**Optional action (recommended for wallet interoperability):**

Ensure your wallet implementation supports `trusted_authorities` in DCQL queries and respects the
automatic population if not explicitly set.

### Integrates `swiyu-sdjwt-verifier` for enhanced SD-JWT verification

The verifier now uses `swiyu-sdjwt-verifier` library for SD-JWT verification, replacing parts of
the inline verification logic. This improves maintainability and compatibility.

**Impact:** No action required; verification behavior should remain consistent.

### Enhanced error handling for presentation verification

The verifier now catches **uncaught `RuntimeException`s during presentation verification** (e.g., DID resolution
failures) and properly marks the verification session as `FAILED` instead of leaving it stuck in `IN_PROGRESS`.

**Impact:** Better observability and faster detection of failed verifications.

## Replaced placeholder digest with pointer record `DisclosureNotProvided`

Missing values in SD-JWT verification are now detected via a `DisclosureNotProvided` pointer instead of
a placeholder digest.

**Testing:** Verify that the system correctly identifies and handles missing SD-JWT disclosures.

## Migration checklist

### Configuration changes

- [ ] Move `Trust Anchor` from request-time to application-level configuration via `SWIYU_TRUST_ISSUER_DID`.
- [ ] Verify that if `SWIYU_TRUST_ISSUER_DID` is set, `SWIYU_TRUST_REGISTRY_API_URL` is also configured.
- [ ] Enable `MANAGEMENT_INCLUDE_AUDIT_DATA` if your clients need audit information in responses (defaults to `false`).
- [ ] Rename deprecated cache properties to explicit `-ms` suffixed versions:
    - `caching.jwk-cache-ttl` → `caching.jwk-cache-ttl-ms`
    - `caching.trust-cache-ttl` → `caching.trust-cache-ttl-ms`
- [ ] Confirm Trust Protocol 2.0 is configured and Trust Protocol 1.0 support is not needed.

### Business verifier / application logic changes

- [ ] Remove any code that sets `Trust Anchor` in `CreateVerificationRequest`.
- [ ] Review and update trust verification logic if you are now creating verifications without a source of trust.
- [ ] Update audit data consumers to handle missing audit fields (unless `MANAGEMENT_INCLUDE_AUDIT_DATA=true`).
- [ ] Update parsers that handle SD-JWT verification results to recognize `DisclosureNotProvided` pointers.

### Wallet / client changes

- [ ] Ensure wallets support DCQL `trusted_authorities` for improved credential filtering.
- [ ] Test that wallets can complete the verification flow with the new audit data handling (omitted by default).

### Testing

- [ ] Verify verifier startup with new configuration (no errors).
- [ ] Test trust validation with Trust Protocol 2.0.
- [ ] Confirm audit data is omitted by default and present when explicitly enabled.
- [ ] Test creation of verifications without a source of trust (if applicable to your use case).
- [ ] Verify SD-JWT verification results correctly represent undisclosed claims.
